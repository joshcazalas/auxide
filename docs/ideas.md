# Ideas

Things Auxide could do and deliberately does not do yet, kept in one place so that
neither half has to be worked out twice.

The second list is the one that earns this file. A feature Auxide lacks gets
suggested again every few months, and without somewhere to write down why it was
turned down, each suggestion costs the same argument. `wontfix` on a closed issue
records the verdict and loses the reasoning.

Nothing here is a commitment or an ordering. The long-form research these came
from — what the rest of the field ships, and what it costs them — is at
<https://claude.ai/code/artifact/96a02832-888e-41bd-ace5-1ba1a4bd010c>.

## What decides these

Auxide is a set of positions before it is a feature set, and a feature that costs
one of them costs more than it looks like it costs:

- `GUILDS` and `GUILD_VOICE_STATES` only — no message content, no presence, no
  member list;
- no database and no retained media, so a queue is a file when it needs to
  outlive a restart;
- no public inbound port;
- nothing that can drift out of step with what Discord was actually handed;
- and where Discord already solved something — per-command permissions, an audit
  log — Auxide delegates instead of reimplementing it.

## Worth doing

### Small

A playhead on `/now-playing`. The position is already read out of Songbird by
`VoiceWorker::seek` to compute relative moves; it just never reaches the card.
Every other bot in the field shows elapsed against total.

Buttons on the now-playing card. `handle_component` and the `auxide:select:…`
custom-ID scheme already exist for search pickers. The detail worth keeping: a
skip button routed through `SkipVerdict` casts a vote on somebody else's track
rather than skipping it, and can say so — which no other bot's buttons do.

`/play-next`, `/move` and `/skip-to`. The queue can be removed from by position,
range and requester, but not reordered. Jumping the queue affects the whole room,
so it plausibly wants the same test skipping does.

`/previous`. It is `/history replay:1` under a name people already reach for.

Dropping queued tracks belonging to people who left, and de-duplicating the
queue. `requested_by` is already on every item and voice-state departures are
already handled for the abandoned-room pause. Departure cleanup should be opt-in;
somebody stepping out for two minutes should not lose their queue.

A configurable vote threshold. Half the channel is hardcoded, and it is the one
piece of governance Discord's per-command editor cannot express.

A sleep timer — `/stop in:30m`, or after the current track. Small against the
existing idle-timer machinery, and the thing anybody actually wants at 2am.

The current track as the voice channel's status, which needs no channel to post
in and no Send Messages permission. Serenity exposes it as
`Http::edit_voice_status` and `EditChannel::status`. Note before building: this
endpoint is **not** in Discord's REST documentation. Libraries implement it and
bots ship it, but it can be withdrawn without a changelog entry, so it wants a
failure path that shrugs rather than one that surfaces.

### Project-sized

**A local library source.** The highest-value item here, and already anticipated
twice — ADR 0001 lists a local file source and names "the player remains usable
with local or future authorized sources if YouTube extraction breaks" as a
consequence, and the operator guide already reserves `/var/lib/homelab/media`
read-only. `SourceResolver` is the seam; a filesystem or Subsonic implementation
needs no subprocess, no rate limit and nothing that can be blocked. Two resolvers
registered together, with `/play` preferring the library and falling back to
YouTube, is also the structural answer to the risk below.

**Named playlists as files.** `/export` already writes the file. What is missing
is a server-side folder, a name, and a loader — which is how JMusicBot has always
done it, and it needs no database and no schema to migrate.

**Autoplay.** The mechanism on YouTube is the autogenerated radio mix, which is
the first entry in `REFUSED_LIST_PREFIXES` — turned down because it never ends
and there is no total to bound an expansion against. That reasoning is right for
queueing a mix and wrong for autoplay, where never ending is the point. The shape
that fits: when the queue empties and autoplay is on, take *one* entry from the
last track's mix that is not already in history, queue it, repeat. Bounded per
step, no new dependency, and the idle timeout still ends a session in a room that
actually emptied.

**A fair queue.** Interleave waiting tracks by requester so one person queueing
fifteen songs cannot lock everybody else out for an hour. It is the same
principle as scoped vote-to-skip applied to ordering instead of interruption, it
is a third mode alongside `RepeatMode` and shuffle, and JMusicBot is close to the
only bot that has it.

**Lyrics.** Normally an argument against itself, because Genius wants an API key.
LRCLIB does not: no key, no registration, no rate limit, plain and time-synced.
With a playhead, the synced version can highlight the current line, which almost
nothing on Discord does.

**SponsorBlock.** Skip sponsor reads inside YouTube videos. Public API, no auth,
segments keyed by video ID; fetch at resolve time and seek past at playback.

**More sources — direct URL, attachment, SoundCloud, Bandcamp.** Each is a
resolver behind the existing trait. The honest cost is the security ledger:
every new container format is another Symphonia parser fed untrusted bytes, which
`Cargo.toml` already treats as a considered cost rather than a free feature.
Direct URL and attachment are cheapest, needing no extractor at all.

**Audio filters.** Cheaper than the `output_volume` comment implies: any level
other than 1.0 already costs Opus passthrough, and the default is 0.5, so that
cost is already paid on every session. Songbird ships no EQ, so this is either
sample-level DSP in the mixer path — `rubato` is already in the tree and covers
speed and pitch — or an ffmpeg subprocess that would not otherwise exist. Worth
confirming somebody actually wants it first.

**Scrobbling.** `.fmbot` scrobbles what music bots play to the Last.fm accounts
of everyone in the voice channel, natively for a handful of bots and by parsing
the now-playing message for the rest. Worth ten minutes to check whether the
existing announce embed is already legible to it.

## Considered and declined

**A song request channel** — a pinned embed where typing a song name queues it.
Genuinely good UX, and it needs `MESSAGE_CONTENT`. The operator guide instructs
the reader to leave privileged intents disabled as a requirement, not a
preference. The part that costs nothing is a pinned now-playing card with
buttons and an "add a track" modal; buttons and modals need no intent at all.

**A web dashboard.** A public listener, an OAuth flow, session storage and an
attack surface, against a design whose stated property is that it needs no public
inbound port. If it is ever wanted, it belongs on the same loopback address as
observability, reachable through something else, and not inside the bot's trust
boundary.

**24/7 mode.** The fifteen-minute hold on an emptied queue is the better default
and is already documented as a deliberate choice. Suppressing the idle disconnect
is a small change if it is ever genuinely wanted; it mostly exists elsewhere
because hosted bots are measured on engagement.

**Caching media locally.** Makes replays instant and contradicts "does not keep
complete media files," which is a source-policy position in the README rather
than an implementation detail.

**Ducking the music when somebody speaks.** Needs voice receive, which now means
DAVE decryption on the inbound path for every speaker, continuously, plus voice
activity detection — for a volume tweak. Songbird can do it. It is not worth it
here.

**Spotify.** Already refused in ADR 0001, on the grounds that the official APIs
do not hand over audio bytes. Every bot advertising Spotify support is resolving
the metadata and playing YouTube.

**A DJ role.** Discord's per-command permission editor already does this, per
command, with an audit log, and without anybody editing a file on the host.

**Prefix commands.** A legacy affordance. Slash-only is right.

## Not this repo

Two ideas from the same research are separate programs rather than features, and
are recorded here only so they are not lost:

- **A multi-track voice recorder.** Songbird already decrypts inbound DAVE per
  speaker and the SSRC mapping gives the per-speaker split, which is the hard
  part and the part that broke most of the ecosystem in March 2026. Recording
  people needs consent handled loudly, not quietly.
- **A media request bot** — friends ask for something with a slash command, the
  request is approved in Discord, and the bot says when it has arrived. Discord
  is a poor alerting surface and a very good place to let people ask for things.

## The risk these sit against

YouTube blocks datacenter IP ranges it associates with scraping, and the bots
still playing reliably are updating yt-dlp on a roughly twelve-hour cycle. A
homelab on a residential connection has the IP profile hosted bots pay proxy
vendors to imitate, which is the good half. The pinned extractor is the exposed
half, and it is a deliberate reproducibility choice in direct tension with that
cadence. `source-check.sh` running daily in CI is the right sensor, but a sensor
reports a break rather than repairing it — so the thing worth deciding before it
happens is what the response is: a fast path to bump the input, or a state
Auxide can report to a channel instead of failing one track at a time.
